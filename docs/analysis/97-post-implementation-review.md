## 4. Verified as correct

Checked and found sound — the lead can skip these:

**Prepared-statement cache.** `store.go:201-222`. The fix is right: `LoadOrStore`'s `loaded` bool at `:214` is the correct signal, and the comment at `:209-213` correctly explains why testing the returned value for `nil` is wrong (`LoadOrStore` returns the value it just stored when `loaded` is false, so `actual != nil` is *always* true and every first call would look like a lost race). The loser branch closes its own duplicate at `:218` and returns the winner's statement. The single call site (`:1750`) never closes the cached `*sql.Stmt`. The `store.go:971` `defer stmt.Close()` is on a **`tx`-scoped** prepare (`UpdateFlagsBatch`), unrelated to the cache — correct. Boundedness claim verified: 16 SQL strings × `MaxOpenConns = 12` = at most 192 driver statements, per-`Store` map, dies with the Store. I searched for the same class of bug elsewhere — `LoadOrStore`/`sync.Map` appears nowhere else in `internal/` or `app/`, and the only other `defer stmt.Close()` is inside a transaction. **No second instance of this bug class.**

**`UpdateContent` timestamp round-trip.** Traced into the driver: `modernc.org/sqlite@v1.42.2/conn.go:127` writes `t.String()`; `conn.go:110` reads it back with a layout special-cased for exactly that form; `rows.go:150-155` returns `time.Time` (not string) for `DATE`/`DATETIME`/`TIMESTAMP` columns, which is why `&d.UpdatedAt` scans at all. The write→read→re-stringify cycle is byte-identical, so `WHERE updated_at <= ?` compares equal for an unchanged row. Fractional-second ordering is also correct (trailing-zero elision in `String()` preserves lexicographic order for decimal fractions). The residual hazards are catalogued as F-10, not as a live precision bug.

**`convListSQL` prebuilt table.** 2 participants × 2 orders × 4 HAVING = 16 variants, all compile-time constants, built once at package init (`:131`). `buildConvListSQL` and `convListSQLFor` agree on the key. Arg order at the call site (`:1755`, `folderID, limit, offset`) matches the query's `?`, `LIMIT ?`, `OFFSET ?`. `orderConvAsc` / `orderConvFTSNewest` — the `latest_date DESC, conv_thread_id ASC` tiebreaker — are sound: `COALESCE(thread_id, id)` is exactly the `GROUP BY` key at `:162`, so it is unique per group and the order is total. Deterministic pagination claim holds.

**`threadMemberIDs` `UNION ALL`.** I specifically checked whether the three-way `UNION ALL` (`:1900-1909`) double-counts a row matching two predicates. It cannot cause a defect: the ids are only fed into `AND m.id IN (...)` (`:1983`), and `IN` is set-semantic. The only cost is a longer placeholder list, and the `> maxBatchPlaceholders` fallback at `:1985` handles that. Correct.

**`needsBodyQuery` two-branch union.** The "top-N over a union is the union of the per-branch top-N" argument at `:1318-1320` is **mathematically correct**: a row in the global top-N has at most N-1 rows ahead of it within its own branch, so it is inside that branch's top-N. Subquery column projection is right — the inner selects emit `<projection>, date`, the compound exposes both, and the outer `SELECT <projection> … ORDER BY date` resolves `date` from the FROM.
